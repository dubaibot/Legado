# 多源功能合并修改清单

> 目标底座：当前工作区「阅读Sigma」（`app/` View 体系，DB v90，Kotlin 2.3.10，minSdk 21）
> 分析日期：2026-10-15。数据来源：四个 fork 的克隆树与工作区逐目录对比。

## 0. 结论

四套功能可以组合到同一个底座上，移植方式为「按功能模块搬代码」，理由与前提：

1. 四个 fork 与工作区同为 Sigma 血脉（arc 自述「继承自 Lyc 维护的 Legado 分支」，max 自述「继承自阅读Sigma」，ng/m 的 `help/gsyVideo`、`ui/browser`、`ui/code` 等目录与 Sigma 同构），包名、实体、工具类体系一致，文件级搬运的摩擦可控。
2. 四个 fork 的 git 历史全部被重写为独立根（gitee 导入型），与工作区无共同提交，git merge / cherry-pick 均不可用，只能做文件级移植 + 人工适配。
3. 工具链一致：五个仓库 Kotlin 均为 2.3.10，AGP/SDK 版本接近（compileSdk 36、targetSdk 36），依赖冲突面小。
4. 唯一结构性前置：工作区是纯 View 体系（`buildFeatures` 仅 buildConfig+viewBinding），而 arc/max/ng 的新功能 UI 是 Jetpack Compose 写的，需要先给底座补 Compose 构建配置。

推荐合并顺序（依赖关系决定）：**基础设施 → M 视频栈 → arc 自动化 → max 调试全家桶 → ng AI 助读**。
理由：视频栈与工作区现有视频功能同文件名强冲突，先解决掉避免后续搬运踩它；自动化是自包含新包、零核心侵入，放在 max 之前验证 Compose 链路；max 的调试模型要织入书源执行核心链，动静最大；ng 的 AI 核心虽独立，但入口要重接到 Sigma 的 View UI，工作量最大且依赖前面各步稳定。

## 6. 执行顺序与验证

```
阶段 0  基础设施      Compose 配置 / DB 迁移框架 / 资源目录准备
阶段 1  M 视频栈      2.1 + 2.2，先出「弹幕保留」融合方案再动文件
阶段 2  arc 自动化    3.1-3.7，验证 Compose 屏 + Service + Room 全链路
阶段 3  max 调试      4.1 → 4.2 → 4.3 三批，每批独立分支 + 独立验证
阶段 4  ng AI        5.1 核心层 → 5.2 入口层
```

每阶段验证基线：
1. `./gradlew :app:assembleDebug` 通过，`assembleRelease` 混淆通过（keep 规则补新增包）。
2. Room schema 导出对比：新增实体迁移后旧数据可升级（用 v90 备份实库跑迁移）。
3. 手测清单：阅读主流程（翻页/听书/换源）回归；每阶段新增功能主路径走通。
4. 弹幕视频专项：阶段 1 后验证明弹幕渲染、音视频同步、后台播放。

## 7. 主要风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| DB 各源独立演进（90→100/113/119） | 同名实体字段分叉（如 Book/RssArticle 在各 fork 加了不同字段） | 每搬一个实体先做三方对比（工作区 vs 源 vs 上游），字段取并集，迁移逐版本写 |
| max 根快照较旧（2026-04-20） | 对 `AnalyzeRule`/`webBook` 的 patch 落点偏移 | 按工作区现行代码重新定位埋点，逐函数 review |
| 视频栈同文件名冲突 | 直接覆盖丢失工作区弹幕功能 | 以 m 壳为基座回挂弹幕层，建独立分支评审 |
| ng UI 重构依赖 | AI 入口组件依赖 `ui/design` 设计系统 | 核心层先落，入口层用 Sigma 原生控件重写 |
| Compose 与 View 混用 | 主题/字体/深色模式两套体系 | Compose 屏统一走 Sigma 的 `ThemeStore` 适配 |
